كيف تستعمل الدليل؟

قبل Docker: لغة الـTerminal

Operating System يدير الذاكرة والملفات والبرامج. Linux kernel هو الجزء الذي يتواصل مع Hardware ويضبط العمليات. Debian توزيعة تجمع Kernel وبرامج وأداة تثبيت Packages اسمها apt. الـTerminal نافذة نصية؛ والـShell برنامج داخلها يفسّر أوامرك.

الملف على القرص ليس برنامجًا يعمل بعد. عند تشغيله يصبح Process وله رقم PID. الـService وظيفة يقدمها برنامج طويل التشغيل، مثل استقبال طلبات الموقع. الخدمة تحتاج Process يعمل، وليس مجرد Package مثبتة.

Permissions: من يقرأ ومن يكتب؟

لكل ملف Owner وGroup، وصلاحيات r للقراءة، w للكتابة، x للتنفيذ. في Directory تعني x السماح بالعبور. chmod 600 يعطي Owner القراءة والكتابة فقط. chmod 755 يسمح بتشغيل Script وقراءته. chown www-data:www-data يغيّر Owner وGroup. تطابق أسماء المستخدمين ليس كافيًا عبر Containers: Linux يقارن أرقام UID/GID.

HTTP · TCP · DNS · FastCGI · SQL

كيف يصل مقال إلى المتصفح؟

Browser هو Client: يطلب صفحة. Server برنامج يستقبل الطلب ويعيد Response. الـIP address يحدد وجهة على الشبكة، والـPort يحدد باب برنامج على تلك الوجهة. TCP ينقل Bytes باتصال مرتب؛ فوقه توجد Protocols تحدد معنى تلك البيانات.

DNS يربط اسمًا مثل login.42.fr بعنوان IP. ملف /etc/hosts يمكن أن يعطي جهازك ربطًا محليًا دون إنشاء DNS عام. HTTP يصف الطلب والجواب، مثل GET / و200 OK. HTTPS هو HTTP داخل اتصال محمي بـTLS. HTML يصف محتوى الصفحة، وCSS مظهرها.

مختبر بصري 01

كن أنت الطلب

اختر نوع الملف، ثم مرّر الطلب خطوة بخطوة.

الخطوة 0: المتصفح يحتاج IP للـDomain أولًا. اضغط «الخطوة التالية».

ثلاث خدمات، ثلاث مسؤوليات

NGINX يستقبل HTTPS ويقرأ الملفات الثابتة. لا ينفذ PHP. PHP لغة يفسرها برنامج على Server؛ PHP-FPM يدير Workers لتنفيذ ملفات PHP. WordPress تطبيق CMS مكتوب بـPHP يدير المقالات والمستخدمين. MariaDB نظام Database: يخزن البيانات في Tables ويجيب عن أوامر SQL.

عند طلب مقال، NGINX يرسل اسم Script ومعلومات الطلب إلى PHP-FPM ببروتوكول FastCGI على wordpress:9000. WordPress يطلب محتوى المقال من mariadb:3306، يبني HTML ويعيده. المتصفح لا يتصل مباشرة بـMariaDB. صورة موجودة يمكن أن يرسلها NGINX دون المرور بـPHP أو Database.

هل يمكن اختبار PHP-FPM هكذا: curl http://wordpress:9000 ؟

الإجابة: لا، PHP-FPM هنا يتحدث FastCGI — Port رقم فقط؛ Protocol هو اللغة. اختبر الموقع عبر NGINX، أو استخدم FastCGI client عند تشخيص PHP-FPM.

الوصفة، النسخة، التشغيل

Dockerfile → Image → Container

Dockerfile وصفة بناء نصية. Image ناتج البناء: Filesystem layers وإعدادات افتراضية، وليست Process تعمل. Container نسخة تشغيل مرتبطة بـImage مع Writable layer وRuntime configuration. تستطيع إنشاء عدة Containers من Image واحدة، ولكل منها حالتها.

التشبيه: Dockerfile وصفة طعام، Image مجموعة مكونات مجهزة وفقها، Container مطبخ ينفّذ الخدمة. حدود التشبيه: Image ليست مجرد وصفة ثانية؛ فيها الملفات الناتجة عن البناء فعليًا. حذف Container لا يحذف Image، وتغيير Dockerfile وحده لا يغيّر Container موجودة.

من ينفّذ الأمر؟

Docker CLI هو البرنامج docker الذي تخاطبه. يرسل طلبًا إلى Docker daemon، واسمه dockerd، الذي يدير Images وContainers وNetworks وVolumes. الاتصال المحلي غالبًا عبر Unix socket في /var/run/docker.sock. Registry مستودع Images؛ pull يجلب Image وpush يرفعها. في المشروع يُسمح بجلب Base image من Debian/Alpine، وتبني Images الخدمات بنفسك.

بيئة واضحة قبل أول Container

جهّز مختبرك داخل VM

أنشئ VM جديدة بتوزيعة Debian مستقرة باستعمال Hypervisor يناسب جهازك. اقتراح تعليمي مريح: 2 CPU، 4 GB RAM، 25 GB disk أو أكثر حسب مواردك؛ هذه ليست أرقامًا يفرضها Subject. نزّل ISO من الموقع الرسمي، اربطها بـVirtual optical drive، شغّل Installer، أنشئ مستخدمًا باسم Login الخاص بك وثبّت النظام. Desktop اختياري؛ Terminal كافية.

الـISO صورة قرص التثبيت. بعد التثبيت أزلها من Virtual drive وأقلع من Virtual disk. اختيار Architecture يجب أن يلائم Hypervisor. شبكة NAT تسهّل Internet داخل VM لكن الوصول إليها من جهازك قد يحتاج Port forwarding؛ Bridged يعطي VM عنوانًا على شبكة جهازك. يمكن أيضًا استعمال Host-only للوصول المحلي مع Adapter ثانٍ NAT للتنزيلات.

تثبيت Docker Engine وCompose plugin

على Debian نظيفة، أضف Repository الرسمي ثم ثبّت الحزم أدناه. إذا سبق تثبيت Docker من مصدر آخر فاتبع صفحة التثبيت الرسمية لمعالجة تعارض الحزم أولًا. أوامر هذه الفقرة تعدّل VM فقط.

قبل إنشاء Volumes المشروع، اقرأ درس Storage لضبط data-root. لا تحتاج إلى تشغيل WordPress أو MariaDB على VM نفسها؛ سنثبتهما داخل Images.

# Validate configuration and initialize required files here.

Networking: أين يوجد localhost؟

داخل كل Container، localhost و127.0.0.1 يشيران إلى تلك Container نفسها. داخل VM يشيران إلى VM، وعلى جهازك يشيران إلى جهازك. لهذا DB_HOST=localhost داخل WordPress يبحث عن MariaDB داخل WordPress، وهي غير موجودة هناك.

أنشئ User-defined bridge network. تحصل Containers المتصلة بها على Network interfaces وعناوين، ويتيح Docker DNS اكتشاف بعضها بالأسماء. في Compose سنستعمل Service names ثابتة: wordpress وmariadb. IP قد تتغير بعد إعادة الإنشاء، لذلك لا تثبّتها في Configuration.

كيف نحقق /home/login/data دون Bind mounts؟

هذا إعداد Docker host كله

data-root ليس خيارًا لService واحدة. تغييره لا ينقل البيانات الموجودة تلقائيًا، وقد يجعل Images وContainers القديمة غير ظاهرة في الجذر الجديد. على VM فيها عمل سابق، خذ Backup واتبع خطة نقل موثقة؛ لا تطبّق وصفة VM الجديدة مباشرة.

Configuration ليست Password

نريد تغيير Domain دون تعديل Image. Environment variable زوج اسم/قيمة يراه Process عند التشغيل. Subject يفرض استخدامها ووجود .env. لكنه لا يفرض أن نخزن Password كنص في Environment؛ يوصي بـDocker secrets لحماية القيم الحساسة.

الآليةوظيفتهامثال
srcs/.envقيم يستخدمها Compose أثناء Interpolation؛ ليست كلها محقونة تلقائيًا في ContainerDOMAIN_NAME=learner.42.fr
environment:ما نمرره صراحةً إلى Process داخل ContainerDOMAIN_NAME: ${DOMAIN_NAME:?Set DOMAIN_NAME}
env_file:حقن مفاتيح ملف إلى بيئة Containerآلية مختلفة عن --env-file للـCompose CLI
secrets:إتاحة File فقط للخدمات التي تحتاجه/run/secrets/db_password
ARGBuild-time configuration وليست سرًاإصدار Source archive

${VAR:?message} يرفض القيمة المفقودة أو الفارغة. ${VAR:-default} يعطي Default. إذا كتبت أمر Shell داخل Compose وتريد أن توسع Container المتغير، فاكتب $$VAR ليتجاوز Compose؛ وإلا قد يوسعه Compose مبكرًا. Shell environment قد تتغلب على قيم .env؛ افحص Configuration عند الشك.

ماذا تفعل Docker secrets في Compose المحلية؟

تعرض ملفات محلية داخل Container غالبًا في /run/secrets/NAME. لا تُشفّر الملف الأصلي على Host تلقائيًا، ولا تحميه من root أو من صاحب الوصول إلى Docker daemon. في Compose المحلية تُنفذ File secrets باستخدام File mounts؛ منع Subject لـBind mounts يخص Volume بيانات WordPress وDatabase، مع توصيته المنفصلة بـSecrets.

الاسم DB_PASSWORD_FILE ليس تعليمة سحرية ينفذها Docker. برنامجك أو Entrypoint يجب أن يقرأ الملف. لا تضع Password في Dockerfile أو Git أو Commands محفوظة في History، ولا تفترض أن حذفها من Commit لاحق يمحوها من History. إذا تسربت، غيّرها وأزلها من History حسب الحالة.

سنستعمل Passwords عشوائية Hex من 64 حرفًا، ونفرض هذه الصيغة في Scripts. هذا يجعل مثال SQL أسهل للفهم دون بناء Parser للهروب من Quotes؛ إذا أردت قبول Passwords حرة، أضف Escaping صحيحًا ولا تُدرج النص الخام في SQL.

MariaDB: من Directory فارغة إلى Database

Database مجموعة بيانات منظمة؛ Table تشبه جدولًا له Columns وRows؛ SQL لغة تعريفها والاستعلام منها. لدينا فرق بين مستخدم Linux اسمه mysql يشغّل Server، ومستخدم SQL اسمه wp_app يستعمل Database، وحسابات WordPress التي تحفظها الجداول لاحقًا.

SQLالمعنى
CREATE DATABASE wordpress;إنشاء مساحة منطقية لبيانات التطبيق.
CREATE USER ...إنشاء هوية اتصال بـDatabase server.

'wp_app'@'%' تعني مستخدمًا يسمح بالاتصال من Hosts مطابقة لـ%، مع Password. هذا مفيد لعناوين Containers المتغيرة، لكنه لا يلغي ضرورة Network مقصودة وعدم نشر 3306. لا نعطيه صلاحيات على *.* ولا صلاحيات root. حساب root@localhost محلي للإدارة.

2. افصل أول Boot عن كل Restart

  1. تحقق من الإعدادات واقرأ Secrets دون طباعتها.
  2. إذا لم توجد System tables، شغّل mariadb-install-db.
  3. شغّل Server مؤقتة بدون TCP، وانتظر Socket بمهلة محدودة.
  4. أنشئ Database والحساب المحدود واضبط root، ثم سجل نجاح التهيئة.
  5. أوقف Server المؤقتة، وشغّل mariadbd في Foreground بواسطة exec.
اعرض Entrypoint كاملة مع معالجة First boot وRestart
ملف المشروع · mariadb/tools/entrypoint.sh
#!/bin/sh
set -eu
: "${DB_NAME:?DB_NAME is required}"
: "${DB_USER:?DB_USER is required}"
for name in "$DB_NAME" "$DB_USER"; do
    case "$name" in ''|*[!a-zA-Z0-9_]*) echo "Use SQL names with letters, digits, underscore" >&2; exit 1;; esac
    [ "${#name}" -le 32 ] || exit 1
done
[ "$DB_USER" != root ] || { echo "DB_USER must not be root" >&2; exit 1; }
read_hex_secret() {
    value=$(cat "$1")
    case "$value" in ''|*[!0-9a-f]*) echo "Expected a hex secret" >&2; exit 1;; esac
    [ "${#value}" -ge 32 ] || { echo "Secret too short" >&2; exit 1; }
    printf '%s' "$value"
}
db_pass=$(read_hex_secret /run/secrets/db_password)
root_pass=$(read_hex_secret /run/secrets/db_root_password)
install -d -o mysql -g mysql /run/mysqld /var/lib/mysql
umask 077
printf '[client]\nuser=root\npassword=%s\nsocket=/run/mysqld/mysqld.sock\n' "$root_pass" > /run/db-root.cnf
printf '[client]\nuser=%s\npassword=%s\nhost=127.0.0.1\nprotocol=tcp\ndatabase=%s\n' "$DB_USER" "$db_pass" "$DB_NAME" > /run/db-health.cnf

if [ ! -d /var/lib/mysql/mysql ]; then
    chown mysql:mysql /var/lib/mysql
    mariadb-install-db --user=mysql --datadir=/var/lib/mysql \
        --auth-root-authentication-method=socket --skip-test-db
fi

if [ ! -f /var/lib/mysql/.inception-ready ]; then
    mariadbd --user=mysql --skip-networking &
    bootstrap_pid=$!
    cleanup() {
        kill -TERM "$bootstrap_pid" 2>/dev/null || true
        wait "$bootstrap_pid" 2>/dev/null || true
        rm -f /run/db-root.cnf
    }
    trap cleanup EXIT
    trap 'exit 143' TERM
    trap 'exit 130' INT
    ready=0
    for attempt in $(seq 1 60); do
        if mariadb-admin --protocol=socket ping --silent >/dev/null 2>&1; then
            ready=1
            break
        fi
        kill -0 "$bootstrap_pid" 2>/dev/null || { echo "Bootstrap exited" >&2; exit 1; }
        sleep 1
    done
    [ "$ready" -eq 1 ] || { echo "Bootstrap timeout" >&2; exit 1; }
    # Try socket auth on first boot; password auth handles an interrupted setup.
    if mariadb --protocol=socket -uroot -e 'SELECT 1' >/dev/null 2>&1; then
        root_mode=socket
    else
        root_mode=password
    fi
    root_sql() {
        if [ "$root_mode" = socket ]; then
            mariadb --protocol=socket -uroot
        else
            mariadb --defaults-extra-file=/run/db-root.cnf
        fi
    }
    root_sql <<SQL
CREATE DATABASE IF NOT EXISTS \`$DB_NAME\`;
CREATE USER IF NOT EXISTS '$DB_USER'@'%' IDENTIFIED BY '$db_pass';
ALTER USER '$DB_USER'@'%' IDENTIFIED BY '$db_pass';
GRANT ALL PRIVILEGES ON \`$DB_NAME\`.* TO '$DB_USER'@'%';
ALTER USER 'root'@'localhost' IDENTIFIED BY '$root_pass';
SQL
    touch /var/lib/mysql/.inception-ready
    mariadb-admin --defaults-extra-file=/run/db-root.cnf shutdown
    wait "$bootstrap_pid"
    trap - EXIT INT TERM
fi
rm -f /run/db-root.cnf
unset db_pass root_pass
exec "$@"

علامة .inception-ready تعني أن إعداد الحسابات نجح، وليست مجرد وجود Directory. IF NOT EXISTS تجعل إعادة خطوات الإنشاء ممكنة بعد انقطاع مبكر. إذا انقطع الإعداد بعد تغيير Password root، يجرب Script الاتصال بالـPassword المحفوظة بدل افتراض Socket authentication دائمًا. إذا فشل SQL لا يصل إلى العلامة.

Idempotency تعني أن إعادة العملية لا تفسد الحالة الصحيحة ولا تكرر البيانات. لا نعيد إنشاء Database أو تغيير Password عند كل Restart بعد وجود العلامة. ملف /run/db-health.cnf بصلاحية 600 يُنشأ كل مرة لاستخدامه في Healthcheck مصادق عليها. Changing secrets بعد Initialization يحتاج Rotation منسقة.

لماذا يوجد sleep 1 هنا؟

هذه محاولة Readiness محدودة بـ60 مرة، تنتهي بنجاح أو فشل، وليست Infinite loop لإبقاء Container حيّة. بعد التهيئة PID 1 هو mariadbd. لا نستخدم while true أو tail -f أو sleep infinity.

PHP-FPM ليس WordPress، وWordPress ليست Database server. FPM يملك Master process وWorkers؛ عندما يستقبل FastCGI request يفسر Worker ملفات PHP. WordPress تستعمل تلك البيئة لبناء HTML وقراءة Database. حزمة php8.2-mysql توفر Driver الضروري لاتصال PHP بـMariaDB.

2. WP-CLI: Configuration دون Installer يدوي

WP-CLI تدير WordPress من Shell. config create يكتب إعداد الاتصال، core install ينشئ Tables والحساب الأول، وuser create يضيف الحساب الثاني. لا يكفي تنزيل WordPress فقط: Subject يطلب أن تكون مثبتة ومهيأة.

اعرض Entrypoint: انتظر Database، هيّئ WordPress، ثم شغّل FPM
ملف المشروع · wordpress/tools/entrypoint.sh

set -eu
: "${DOMAIN_NAME:?}" "${DB_NAME:?}" "${DB_USER:?}"
: "${WP_TITLE:?}" "${WP_OWNER:?}" "${WP_OWNER_EMAIL:?}"
: "${WP_READER:?}" "${WP_READER_EMAIL:?}"
owner_lower=$(printf '%s' "$WP_OWNER" | tr '[:upper:]' '[:lower:]')
case "$owner_lower" in *admin*) echo "Choose an owner name without admin" >&2; exit 1;; esac
[ "$WP_OWNER" != "$WP_READER" ] || { echo "Use two different WP users" >&2; exit 1; }
for name in "$DB_NAME" "$DB_USER"; do
    case "$name" in ''|*[!a-zA-Z0-9_]*) echo "Invalid SQL name" >&2; exit 1;; esac
done
read_hex_secret() {
    value=$(cat "$1")
    case "$value" in ''|*[!0-9a-f]*) echo "Expected a hex secret" >&2; exit 1;; esac
    [ "${#value}" -ge 32 ] || exit 1
    printf '%s' "$value"
}
db_pass=$(read_hex_secret /run/secrets/db_password)
owner_pass=$(read_hex_secret /run/secrets/wp_owner_password)
reader_pass=$(read_hex_secret /run/secrets/wp_reader_password)
umask 077
printf '[client]\nuser=%s\npassword=%s\nhost=mariadb\nprotocol=tcp\ndatabase=%s\n' \
    "$DB_USER" "$db_pass" "$DB_NAME" > /run/wp-db.cnf

for attempt in $(seq 1 60); do
    if mariadb --defaults-extra-file=/run/wp-db.cnf -e 'SELECT 1' >/dev/null 2>&1; then
        ready=1
        break
    fi
    sleep 1
done

    cp -a /opt/wordpress/. /var/www/html/
fi

# Pass the DB password via stdin, not command-line arguments.
# A temporary file keeps an interrupted write from corrupting wp-config.php.
printf '%s\n' "$db_pass" | wp --allow-root config create \
    --dbname="$DB_NAME" --dbuser="$DB_USER" --dbhost=mariadb:3306 \
    --dbcharset=utf8mb4 --skip-check \
    --config-file=/var/www/html/wp-config.next.php --force --prompt=dbpass

chown www-data:www-data /var/www/html/wp-config.next.php
mv /var/www/html/wp-config.next.php /var/www/html/wp-config.php

    printf '%s\n' "$owner_pass" | wp --allow-root core install \
        --url="https://$DOMAIN_NAME" --title="$WP_TITLE" \
        --admin_user="$WP_OWNER" --admin_email="$WP_OWNER_EMAIL" \
        --skip-email --prompt=admin_password
fi

    printf '%s\n' "$reader_pass" | wp --allow-root user create \
        "$WP_READER" "$WP_READER_EMAIL" --role=subscriber --prompt=user_pass
fi
# Normalize permissions so NGINX can read shared files, PHP can write uploads.
chown -R www-data:www-data /var/www/html
find /var/www/html -type d -exec chmod 755 {} +
find /var/www/html -type f -exec chmod 644 {} +
chmod 640 /var/www/html/wp-config.php
unset db_pass owner_pass reader_pass

نختبر SQL الفعلية حتى إذا بدأنا WordPress خارج ترتيب Compose. core is-installed يفحص Installation داخل Database، وليس مجرد وجود ملفات. الـ--prompt يقرأ Password من stdin، فلا نضعها حرفيًا في Arguments. الـ--allow-root استثناء صريح لأوامر الإعداد داخل Container؛ طلبات الموقع تنفذها Workers كمستخدم www-data.

ملف wp-config.php يحتوي DB password، لذا بيانات Volume وBackups نفسها حساسة حتى مع استخدام Docker secrets. نمنع تنزيله في NGINX ونضع Permissions مقيدة. يعاد توليد إعداد الاتصال عند Boot؛ تغيير Domain بعد Install يحتاج أيضًا تحديث WordPress URLs في Database، وتغيير Password الحسابات الموجودة يحتاج أوامر تغيير فعلية.

ماذا يعني Idempotent هنا؟

إعادة التشغيل لا تعيد تنزيل الملفات فوق uploads، ولا تعيد Install أو إنشاء حساب موجود. مع ذلك، عملية WordPress installation متعددة الخطوات ليست Transaction واحدة: إذا انقطع أول Boot، افحص Logs وحالة الجداول والحسابات. لا تحذف Volume تلقائيًا لمعالجة كل خطأ.

NGINX وTLS: الباب الوحيد للموقع

TLS certificate تربط Domain بـPublic key، ويحفظ Server الـPrivate key سرًا. أثناء TLS handshake يتفق الطرفان على حماية الاتصال. التشفير وحده لا يكفي لإثبات هوية Server؛ يحتاج Client إلى الثقة بالجهة التي وقّعت Certificate والتحقق من مطابقة الاسم.

للمختبر المحلي سنستعمل Self-signed certificate: نوقعها بأنفسنا. الاتصال يستطيع أن يكون مشفرًا، لكن Browser لا يثق بنا تلقائيًا. SAN، أي Subject Alternative Name، يحتوي Domain التي تصح لها الشهادة. ملف hosts لا يصدر Certificate ولا يجعلها موثوقة.

1. أنشئ Certificate محلية مرة واحدة

من جذر المشروع داخل VM، عيّن Domain الحقيقية نفسها الموجودة في .env. الملفات التالية محلية في secrets ومُستثناة من Git.

Terminal · داخل VM
DOMAIN_NAME=YOUR_LOGIN.42.fr
umask 077
openssl req -x509 -nodes -newkey rsa:2048 -sha256 -days 365 \
    -keyout secrets/tls_key.pem \
    -out secrets/tls_cert.pem \
    -subj "/CN=$DOMAIN_NAME" \
    -addext "subjectAltName=DNS:$DOMAIN_NAME"
openssl x509 -in secrets/tls_cert.pem -noout -subject -dates -ext subjectAltName

-nodes تعني هنا أن Private key لا تتطلب Passphrase عند بدء الخدمة، لذلك نحمي الملف بـPermissions. جدد Certificate عند انتهاء صلاحيتها. بقاؤها في secrets يحافظ على نفس الشهادة عبر Recreate بدل توليد شهادة مختلفة كل مرة.

2. ابنِ NGINX من Debian

ملف المشروع · srcs/requirements/nginx/Dockerfile
FROM debian:bookworm
RUN apt-get update && apt-get install -y --no-install-recommends \
    nginx gettext-base curl ca-certificates \
    && rm -rf /var/lib/apt/lists/* /etc/nginx/sites-enabled/default

نزيل Default site الخاصة بالحزمة لكي لا نستمع بالخطأ على 80. gettext-base توفر envsubst لتوليد Configuration من Template. Docker لا يحوّل ${DOMAIN_NAME} داخل أي ملف عشوائي تلقائيًا.

ملف المشروع · nginx/conf/default.conf.template
server {
    listen 443 ssl;
    server_name ${DOMAIN_NAME};
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_certificate /run/secrets/tls_cert;
    ssl_certificate_key /run/secrets/tls_key;
    root /var/www/html;
    index index.php index.html;
    client_max_body_size 16m;
    access_log /dev/stdout;
    error_log /dev/stderr warn;

    location / {
        try_files $uri $uri/ /index.php?$args;
    }
    location ~* ^/wp-config.*\.php$ {
        deny all;
    }
    location ~ /\. {
        deny all;
    }
    location ~* ^/wp-content/uploads/.*\.php$ {
        deny all;
    }
    location ~ \.php$ {
        try_files $uri =404;
        include fastcgi_params;
        fastcgi_pass wordpress:9000;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        fastcgi_param HTTPS on;
    }
}

root هو مسار ملفات الموقع كما تراها NGINX. يجب أن يكون الملف نفسه موجودًا عند /var/www/html داخل WordPress لأن SCRIPT_FILENAME يرسل المسار إلى FPM. try_files يبحث عن ملف موجود، وإلا يوجه الطلب إلى Front controller اسمه index.php. إذا طلب أحد ملف PHP غير موجود نعيد 404 قبل FastCGI.

fastcgi_pass يحدد الخدمة والبروتوكول ضمنيًا عبر Module؛ لا تستبدله بـproxy_pass http://wordpress:9000. HTTPS on يخبر PHP أن طلب العميل وصل عبر HTTPS، لتنتج WordPress الروابط الصحيحة. الاتصالات الداخلية هنا ليست TLS إضافية؛ TLS تنتهي في NGINX. لا ننشر Port 80 حتى لو بدا HTTP-to-HTTPS redirect ملائمًا، لأن Mandatory يطلب 443 فقط.

ملف المشروع · nginx/tools/entrypoint.sh
#!/bin/sh

case "$DOMAIN_NAME" in *[!a-zA-Z0-9.-]*|'') echo "Invalid domain" >&2; exit 1;; esac
[ -s /run/secrets/tls_cert ] && [ -s /run/secrets/tls_key ]
envsubst '${DOMAIN_NAME}' < /etc/nginx/templates/default.conf.template \
    > /etc/nginx/conf.d/default.conf
nginx -t
exec "$@"

نمرر إلى envsubst اسم ${DOMAIN_NAME} فقط وبين Single quotes، كي تبقى متغيرات NGINX مثل $uri و$document_root سليمة. تشغيل envsubst دون تقييد قد يحولها إلى نص فارغ ويفسد Routing. nginx -t يفحص Syntax وفتح ملفات مطلوبة، ثم exec يبدأ الخدمة في Foreground.

ربط Domain بالـIP على الجهاز الذي فيه Browser

استخرج IP الـVM عبر ip -br address. إذا كنت تتصفح من جهازك وكانت VM قابلة للوصول بعنوان 192.168.56.10 مثلًا، حرر /etc/hosts على جهاز Browser وأضف سطرًا مثل التالي مع عنوانك الفعلي. Windows يستعمل الملف C:\Windows\System32\drivers\etc\hosts بصلاحية Administrator.

جهاز Browser · hosts · مثال IP، استبدله
192.168.56.10 YOUR_LOGIN.42.fr

إذا Browser داخل VM، يمكن ربط Domain بـ127.0.0.1 هناك. إذا استعملت NAT port forwarding من جهازك إلى VM، اربط Domain بعنوان جهة الـHost للـForwarding واختبر وصول 443→443. تعديل hosts داخل Container وحدها لن يساعد Browser على جهازك. hosts يغير Name resolution، وليس HTTP redirect.

اختبار محلي موثوق دون تعديل DNS

داخل VM، من جذر المشروع:

    --resolve "$DOMAIN_NAME:443:127.0.0.1" \

--resolve يحدد IP لاتصال curl فقط مع الحفاظ على Domain في Host وTLS SNI. SNI تخبر Server باسم الموقع أثناء TLS handshake. --cacert تجعل curl تثق بالشهادة المحلية لهذا الطلب. المتوقع HTTP 200 أو Redirect مشروع إلى نفس Domain، وليس 502 أو Redirect إلى localhost أو HTTP.

3. Persistence باختبار قبل/بعد

  1. سجّل دخول WordPress، أنشئ Post بعنوان مميز وارفع صورة.
  2. نفّذ make down ثم make.
  3. تحقق من وجود Post، عرض الصورة، وإمكانية الدخول بنفس الحساب.
  4. أعد تشغيل VM نفسها، ثم افحص عودة Stack بعد بدء Docker daemon. لا تسبق هذا الاختبار بـmake stop لأن unless-stopped تحفظ طلب الإيقاف اليدوي.

هذه التجربة تثبت بقاء Database وFiles عبر Recreate، وهو أقوى من Restart لنفس Container. docker compose down -v يحذف Volumes العادية للمشروع وبياناتها؛ لا تستعمله في اختبار Persistence أو كعلاج تلقائي للأخطاء.

    -CAfile secrets/tls_cert.pem -verify_hostname "$DOMAIN_NAME" \
    -verify_return_error -tls1_2 < /dev/null
openssl s_client -connect 127.0.0.1:443 -servername "$DOMAIN_NAME" \
    -CAfile secrets/tls_cert.pem -verify_hostname "$DOMAIN_NAME" \
    -verify_return_error -tls1_3 < /dev/null
openssl s_client -connect 127.0.0.1:443 -servername "$DOMAIN_NAME" \
    -tls1_1 < /dev/null
curl --connect-timeout 3 -I http://127.0.0.1:80

الأول والثاني يجب أن ينجحا وتطابق Certificate الاسم. اتصال TLS 1.1 يجب ألا ينجح، وPort 80 لا يقدم خدمة المشروع. بعض OpenSSL clients الحديثة ترفض TLS 1.1 محليًا قبل الاتصال؛ ففشل هذا الأمر وحده لا يثبت رفض Server. افحص أيضًا dc exec nginx nginx -T وفعالية ssl_protocols TLSv1.2 TLSv1.3، واستعمل Client اختبار تدعم Legacy TLS إذا احتجت إثبات تفاوض فعلي.

5. Crash recovery دون تخريب Database

ابدأ بـNGINX لأنها لا تخزن بيانات قابلة للتلف. بعد تشغيلها لأكثر من 10 ثوانٍ، احفظ RestartCount، ثم أنهِ PID 1 من Host عبر PID الفعلية، لا بواسطة docker stop. هذا يوقف خدمة NGINX عمدًا لحظات داخل VM التعليمية.

Terminal · داخل VM
nginx_id=$(dc ps -q nginx)
docker inspect "$nginx_id" --format '{{.RestartCount}}'
nginx_host_pid=$(docker inspect "$nginx_id" --format '{{.State.Pid}}')
case "$nginx_host_pid" in ''|*[!0-9]*) echo 'Invalid PID';; *)
    if [ "$nginx_host_pid" -gt 1 ]; then sudo kill -KILL "$nginx_host_pid"; fi;; esac
# Wait a few seconds, then inspect:
docker inspect "$nginx_id" --format '{{.State.Status}} {{.RestartCount}}'
dc ps

المتوقع زيادة RestartCount وعودة الموقع. هذه حالة مختلفة عن unhealthy مع Process ما زالت حية. لا تجعل اختبار Crash أول تجربة على Database ثم تتفاجأ باستعادة Crash recovery لبياناتها.

Backup ليست Persistence

Volume تنجو من حذف Container، لكنها لا تنجو من حذف Volume أو تلف قرص VM. Backup نسخة مستقلة قابلة للاستعادة. للموقع تحتاج SQL dump وFiles archive متوافقتين زمنيًا؛ أرشفة ملفات Database الحية عشوائيًا قد لا تكون متسقة.

مثال Backup لموقع متوقف عن الكتابة

من جذر المشروع، أوقف NGINX وWordPress مؤقتًا لمنع تغيير الملفات أثناء النسخ. تبقى MariaDB تعمل لإنتاج SQL dump. الأرشيفان يحتويان معلومات حساسة؛ directory المستعملة خارج Repository.

Terminal · داخل VM
backup_dir="$HOME/inception-backup-$(date +%Y%m%d-%H%M%S)"
mkdir -m 700 "$backup_dir"
dc stop nginx wordpress
(umask 077; dc exec -T mariadb mariadb-dump \
    --defaults-extra-file=/run/db-health.cnf --single-transaction --skip-lock-tables \
    --databases wordpress > "$backup_dir/database.sql")
(umask 077; docker run --rm \
    --mount source=inception_wp_data,target=/site,readonly \
    debian:bookworm tar -C /site -czf - . > "$backup_dir/site.tar.gz")
dc start wordpress nginx

استبدل wordpress في dump إذا غيرت DB_NAME. افحص Exit codes وحجم الملفات وصحتها قبل اعتبارها Backup ناجحة. عند Restore في بيئة اختبار: شغّل MariaDB المهيأة، استورد SQL إلى Database المناسبة، أوقف WordPress، أعد Files إلى Volume مع حفظ UID/GID، ثم شغّل الخدمات وافحص المقال والصورة. نجاح الاستعادة هو اختبار Backup الفعلي؛ لا تجرب الاستعادة لأول مرة فوق بياناتك الوحيدة.

قائمة التحقق الشخصية

ضع علامة عندما تملك دليلًا عمليًا، لا لمجرد أن الملف يبدو صحيحًا. تُحفظ العلامات محليًا في Browser إذا سمحت بإتاحة Local storage.

أسئلة Defense لا تجب عنها بحفظ المصطلح

أين يوجد المقال وأين توجد الصورة؟

نص المقال ومعلوماته في MariaDB volume، والصورة الفعلية في WordPress files volume. NGINX تقرأ الصورة من Volume المشتركة. أبرهن بإنشاء Post وصورة ثم Recreate للخدمات والتحقق منهما.

ماذا يحدث إذا عطلت MariaDB وNGINX ما زالت Up؟

Up لا تعني نجاح كل وظيفة. قد تعمل ملفات Static وتفشل صفحات تحتاج SQL. أفحص Logs وSQL health وأميز Restart للـProcess عن Healthcheck. لا أعالج ذلك بنشر 3306 للعالم.

كيف تغيّر Domain أثناء Evaluation؟

أحدّث .env، وhosts على جهاز الاختبار، وCertificate ذات SAN الجديدة، ثم WordPress home/siteurl في Database، وأعيد إنشاء الخدمات التي تغيرت Environment لديها. أختبر Redirects وTLS. تغيير server_name وحده غير كافٍ.

لماذا اخترت data-root بدل driver_opts مع bind؟

هذه النسخة تمنع Bind mounts لتخزين البيانات. data-root يغير مكان تخزين Docker داخل VM، ثم أنشئ Named volumes عادية وأثبت ذلك بـvolume inspect وMountpoints. أوثق أن القرار يؤثر على Docker daemon كلها، وأنه لا ينقل البيانات القديمة تلقائيًا.
